# MorphRing v0.2 parity plan: every Filee feature

Generated by the parity audit (reverse-engineering, critic and planning teams) on 2026-10-17.
Same rules as PLAN-v0.2.md: one commit per task, files owned per task, deps serialise overlaps.
Tasks with a CI list must pass GitHub Actions on those OSes; behaviour that only a real desktop can
show goes in the commit body as `Unverified:` lines.

## MorphRing v0.2 Filee parity plan

I read the audit (about 350 features) against `docs/PLAN-v0.2.md` and the in-flight branches. Every feature marked partial, missing or deferred-in-plan that is not blocked from outside now maps to tasks **PX-01 to PX-189**, one commit each.

I checked the task graph with a script (scratchpad `px/graph.py`). It finds **no file conflicts**: any two tasks that touch the same file are ordered by `deps`. The longest dependency chain is 18 tasks.

The groundwork comes first, in the same "skeleton" style as P2-02/P2-03/P2-06. These tasks fill in the shared files once, so later tasks never have to edit them:
- **Core:** PX-01 to PX-04 (formats, options, edge flags and planner tuning, settings)
- **Workspace dependencies:** PX-05
- **Engines skeleton:** PX-06
- **Built-in presets, profiles and library upgrade:** PX-07 to PX-09
- **CLI skeleton:** PX-10
- **Platform skeleton:** PX-11
- **App skeleton and settings window:** PX-12 and PX-13

Feature counts per area are approximate. Some features are split across several tasks (the CAD, document-model, font and downloader engines), and some audit items appear in two areas.

**Choices worth checking:**
- **DWG files** go through the external LibreDWG tool (`dwg2dxf`, GPL), because no Rust library reads DWG.
- **HWP files** use the external rhwp and unhwp tools.
- **Read-only archives** use the system `bsdtar`. Windows 10+ and macOS already ship it, which takes the place of Filee's bundled 7-Zip.
- **Engines for PDF to image and text without Poppler** use hayro and pdf-extract. They cost slightly more than Poppler, so Poppler still wins whenever it is installed.
- **The update check only notifies, and is off by default**, per the "offline unless opted in" rule. It shows the new version and opens the download page; it does not install anything.
- **Windows 11 menu:** PX-169 and PX-170 ship it unsigned, as Filee does, with one admin prompt at install.

**Can't be checked by an agent:** any task that changes how things behave on a real Windows desktop, Mac or X11 session (marked `ci` windows/macos) says to record those checks as `Unverified:` in the commit body.

**Blocked, needs you:** 7 features need code signing, Apple notarization or sponsorship accounts that only you can set up; each is listed with what you would need to do.

## Blocked on the owner

| Feature | Why | What the owner must do |
|---|---|---|
| Windows 11 main context menu entry as a signed per-user package (General page, no admin prompt) | A sparse MSIX package installs per user without admin only when it is signed by a trusted code-signing certificate. PX-169/PX-170 ship Filee's unsigned variant instead, which needs one UAC prompt (admin, all users). | Get an Authenticode code-signing certificate (Certum open-source, SignPath OSS approval or Azure Artifact Signing), add it as GitHub Actions secrets, then a follow-up task signs the package and drops -AllowUnsigned. |
| In-app update download and install (SHA-256 verified installer run silently; tauri-plugin-updater) | tauri-plugin-updater and silent installs need signed builds; unsigned installers trigger SmartScreen and Gatekeeper. PX-143 covers the notify-only check and opens the release page. | Set up code signing (Windows certificate, Apple Developer ID at $99/year with notarytool credentials) and an updater signing key pair stored as secrets. |
| Tray 'Update to x.y.z' that installs the update (with download %) | Same as in-app install: needs signed builds. PX-143 adds a tray item that opens the download page instead. | Same as above: code-signing and notarization accounts and secrets. |
| Code signing for the Windows installer/exe and macOS notarisation | Needs paid certificates and accounts the owner has not set up (PLAN-v0.2 section 5). | Buy or apply for a Windows code-signing certificate (or SignPath OSS) and an Apple Developer ID; add the secrets to the repo. |
| README code signing policy section | A policy section only makes sense once a signing provider is chosen (SignPath requires a specific policy text). | Choose the signing provider; then the policy text can be added from its template. |
| Sponsor window (GitHub Sponsors, Patreon, Ko-fi, PayPal) and supporters list | Needs the owner's sponsorship accounts and links. | Create the sponsorship accounts you want and share the URLs (and a supporters list source if wanted). |
| README Sponsor section and .github/FUNDING.yml | Needs the owner's GitHub Sponsors/Patreon/Ko-fi account names. | Create the accounts and provide the usernames for FUNDING.yml. |
